# Продукт и требования

## Цель и пользователи

Демо поиска по каталогу Softline для преимущественно юридических лиц.
Покупатель находит подходящие товары; сотрудники видят поисковый спрос,
проблемные запросы и обоснованные предложения по улучшению каталога.
Оценка заказчика — по демо; бизнес-эффект является гипотезой до эксперимента.

## Граница MVP

Три представления: поиск покупателя, аналитика сотрудников, разбор запроса.
Поиск содержит подсказки, фильтры, карточки, варианты лицензий и рекомендации.
Разбор показывает этапы обработки и причины выдачи отдельно от клиентского экрана.
Чат, оплата, личный кабинет, интеграция с реальным магазином, автоматические
правки каталога и онлайн-сбор цен конкурентов не входят в MVP.

## Функциональные требования

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| R-01 | Искать по реальному содержимому предоставленного снимка. | Каждый результат связан с существующим продуктом/предложением снимка. |
| R-02 | Учитывать синонимы, сленг, опечатки, раскладку и аббревиатуры. | На размеченных сценариях достигается нужная цель; исходный запрос сохраняется. |
| R-03 | Различать намерения и ограничения. | «Сервер» и «ПО для сервера» различаются; версии и условия лицензии не теряются. |
| R-04 | Учитывать категорию, сегмент и историю сессии. | Контекст задаётся явно, влияет объяснимо и не переносится между сессиями. |
| R-05 | Показывать минимум четыре товара, когда это обосновано каталогом. | Базовое правило: разные продукты; при нехватке — явное ограничение, без случайного заполнения. Требует уточнения O-004. |
| R-06 | Разделять совпадения, альтернативы и сопутствующие решения. | Тип каждой карточки явно указан; ограничения не маскируются. |
| R-07 | Давать рекомендации с доказательствами. | У рекомендации есть source URL, дата проверки и ограничения; цена и наличие берутся из feed. |
| R-08 | Показывать подсказки во время ввода. | Подсказки работают без генеративной модели; устаревший ответ не заменяет новый. |
| R-09 | Логировать поиск и действия. | События связаны с запросом, не дублируются при повторной доставке. |
| R-10 | Давать аналитику сотрудникам. | Показатели выводятся из событий; гипотезы отсутствия товара отделены от фактов. |
| R-11 | Позволять объяснить обработку запроса на демо. | Разбор отражает фактически выполненные шаги и запасной режим. |
| R-12 | Поддерживать демонстрационные бизнес-сигналы отдельно. | Маржа/популярность используются только при наличии данных; synthetic значения помечены. |

## Нефункциональные требования

| ID | Требование | Критерий приёмки |
| --- | --- | --- |
| N-01 | Воспроизводимый локальный запуск. | По будущему README запускаются UI, backend, PostgreSQL и Elasticsearch. |
| N-02 | Ограниченная память при импорте. | Используется потоковый XML decoder; пиковая память измеряется на полном feed. |
| N-03 | Управляемая стоимость. | До массовой индексации оценён бюджет; расход и лимиты наблюдаемы. |
| N-04 | Устойчивость к OpenAI API. | Тайм-аут, 429, отказ и некорректный ответ не останавливают лексический поиск. |
| N-05 | Безопасное обращение с данными. | Секреты остаются на backend; тексты источников не исполняются как инструкции. |
| N-06 | Измеримое качество и скорость. | Фиксируются baseline, метрики и p50/p95; пороги утверждаются после пилота. |

Размер компьютера, лимиты API, версии компонентов и численные SLO пока не согласованы.
