# Полный векторный корпус

SDD: следующий шаг hybrid-v1. Тексты готовятся только из feed, без разметки
запросов/целей и без чтения holdout. Пилот 512 групп сохраняется отдельно.

## Инварианты

- Корпус содержит один представитель каждой пары vendor-path/group_id;
  без group_id — отдельный SKU с OfferID, без придуманной группы.
- Выбор представителя и bounded HTML-clean text сохраняют embedding-text-v1,
  поэтому ранее оплаченные тексты переиспользуются по прежним cache key.
- Обязательны версия корпуса, модель/размерность, SHA исходного feed,
  число предложений и канонический fingerprint. Документы отсортированы,
  ID уникальны. Цены, наличие и тестовые цели не входят в JSON корпуса.
- План читает кэш порциями и считает верхнюю стоимость только уникальных
  отсутствующих текстов. План и replay не вызывают Provider.
- Live требует OPENAI_LIVE_ENABLED=true и явный fingerprint разрешённого
  корпуса. Все вызовы через общий Runtime и ledger $5; не более $0.15
  резервов за один запуск CLI, включая повторы. После рестарта кэш переиспользуется,
  unresolved не удаляются. Пилотный лимит Runtime $0.05 на вызов не повышается:
  индексатор передаёт ограниченные порции и остаток общего лимита запуска.
- Перед сетью проверяются весь корпус и соответствие активному feed/нормализации.
  Поздняя ошибка оставляет частичный кэш, но не готовый поисковый корпус.
- Поиск загружает из кэша только полный корпус. В памяти сохраняет первые
  512 float64-компонент (около 51 МБ для 12.5 тыс. документов), а не все 1536.
  После загрузки повторный запрос не читает весь корпус из PostgreSQL.
- Новые запросы по умолчанию cache-only. Live включается отдельно, через тот же
  Runtime; сбой/исчерпание бюджета/неполный корпус дают BM25 fallback. Конкретный
  SKU проходит прежние фильтры до collapse и повторную application-проверку.

## Приёмка

Domain: неверная версия/модель/SHA, дубли, неправильный vendor URL, пустой текст,
смешанная group/SKU identity и изменённый fingerprint отклоняются.
Application: план с дублями текста и кэшем; отсутствие оплат в plan/replay;
ограничение общего run cap до очередной порции, ошибка и повтор из кэша.
Python: plain/gzip XML, fallback SKU, сортировка и сохранение текста пилота.
ES: SKU без группы не превращается в group_id и не теряет фильтры/проверку vendor.
Полный feed: количество/хэши/стоимость и покрытие кэша записываются в отчёт.
Новый live-запуск выполняется только после разрешения на подготовленный корпус.

## Команды

```powershell
python scripts/prepare-vector-corpus.py --feed C:/Users/hypoc/Downloads/Mindbox.yml.gz.xml
go run ./cmd/vector-index -mode plan
# Только для явно разрешённого корпуса и включённого OPENAI_LIVE_ENABLED:
go run ./cmd/vector-index -mode live -approved-sha 25bac9e399ea4b9bd1a3b11d70dc9d054e33f17ab44655c8b47ae0e9bf8b855e
go run ./cmd/vector-index -mode replay
go run ./cmd/search -query "сервер" -vector-corpus artifacts/vector-corpus.json
# Новые тексты отправляются только при дополнительном явном флаге:
go run ./cmd/search -query "нужно удалённо управлять компьютерами сотрудников и помогать им с настройками" -vector-corpus artifacts/vector-corpus.json -live-query
```

Последняя формулировка заранее выбрана для одного live smoke-запроса; она не
добавляется в разметку и не используется для независимого заявления о качестве.
Сравнение разрешённых development-наборов выполняется cache-only:

```powershell
go build -o bin/search.exe ./cmd/search
python scripts/evaluate-tuning.py --vector-corpus artifacts/vector-corpus.json --batch --output artifacts/full-vector-tuning.json
python scripts/evaluate-tuning.py --vector-corpus artifacts/vector-corpus.json --batch --probes --output artifacts/full-vector-probes.json
```

`search -batch` читает JSON-строку запроса на каждой строке stdin и пишет один
результат на строку, сохраняя процесс и загруженный корпус. Это позволяет измерять
набор без 60 повторных чтений всех векторов. Время batch — суммарное с холодной
загрузкой, а не пользовательский p95; индивидуальная задержка пока не заявляется.

## Политика hybrid-v2 после полного development-прогона

Первый полный прогон v1/.35 сохранил 52/52 целевых групп и 6/6 брендов, но дал
нерелевантные ответы на оба отрицательных запроса: близость 0.39652 и 0.35665.
Порог поднят до **0.45**, без изменения модели, векторов, RRF k=60 и окна 50.
Слабые кандидаты отбрасываются до выбора SKU; ради четырёх карточек они не добавляются.
Это консервативная настройка на development-данных, не откалиброванная вероятность
релевантности и не доказательство отсутствия других ложных совпадений.
Trace содержит ограниченный список кандидатов с cosine и выбранные family ID.

Итог v2: tuning **52/52 групп, 6/6 брендов, 2/2 отрицательных**, ошибок 0.
Batch 60 запросов — 12.049 с вместе с загрузкой процесса/корпуса; это не p95.
Замороженные probes — **5/16** известных положительных групп, ошибок 0;
batch 16 запросов — 14.113 с. На полном v1 тоже 5/16, на ограниченных 512
документах v1 было 13/16. Это различный охват поиска: появились дополнительные
товары и альтернативы, которых нет в неполных положительных метках. Есть также
реальные ошибки намерений (например, виртуальная инфраструктура смешивается
с 3D-сценами). Не добавляли новые положительные метки после просмотра.
Дальнейший разбор задач/роли продукта и независимая оценка остаются следующими этапами;
четыре проверенных релевантных семейства/допродажи ещё не обеспечены.

Во время проверок исправлено восстановление isolated pilot index после медленного
PUT: повтор мог получить resource_already_exists_exception. Продолжаем и очищаем
индекс только при точном совпадении owner + DatasetSHA. Чужой корпус не принимается
и не удаляется; красный/зелёный mock-тест и реальный Elasticsearch проверяют сценарий.

и проверка смысловой пригодности кандидатов на development-наборе.
