# Приоритет явного названия продукта

## Проблема и границы

Development tuning: lexical ставит целевое ПО первым в tune-045/046, а
hybrid-v2 поднимает аппаратные сканеры выше. Одинаковое голосование RRF
не различает точное совпадение имени и соседство по общему слову.
Holdout для выбора этого изменения не запускается и не анализируется.

## Ожидаемое поведение

- После обычных фильтров и RRF приоритет получают lexical-семейства, у которых
  все слова одного допустимого варианта запроса есть в ProductName.
- Слова сравниваются целиком, без fuzzy, подстрок и Description/CategoryNames.
  Используются существующие нормализация/алиасы/транслитерация; не новые группы.
- Для однословного варианта требуется равенство всего ProductName; иначе
  общие слова вроде backup не создают сильное совпадение.
- Приоритетные семейства сохраняют lexical-порядок и lexical SKU; остальные
  сохраняют RRF-порядок. Семейство занимает максимум одно место.
- Price priority, SKU eligibility, exact-ID, fallback и отмена остаются
  прежними. Нет обхода фильтров или дополнения случайными товарами.
- HybridVersion меняется; trace показывает число приоритетных семейств.
  Новый индекс/эмбеддинги для этого правила не нужны.

Проверки до реализации: конфликт lexical identity против semantic consensus,
ложное совпадение в описании/части слова, транслитерация, однословные границы.
Application проверяет применение после resolve, сохранение SKU и отсутствие
влияния на открытый запрос без совпадения имени. Измерение: 60 tuning + 16
development probes, отдельно target@1/@4. Это не новая независимая оценка.

## Диагностика до изменения

Tuning: group hit@4 52/52, brand 6/6, negatives 2/2; probes 7/16.
Среди девяти промахов probes: шесть не имеют целевой группы в векторном окне;
три имеют кандидата (probe-02 rank25, probe-03 rank2, probe-16 rank12), но
для объяснения нужна проверка доступных SKU и ранга. Наличие кандидата
не доказывает ошибку ранжирования. Probe-03 уже имеет известное ограничение
лицензий перехода (capacity-extensions.md). Новый приоритет имён не решает
покрытие task-запросов и не должен обходить это ограничение.

## Измеренный эффект

Hybrid-v3: target group@1 на tuning 50/52 → 52/52; @4 52/52 → 52/52.
Изменился ранг tune-045/046: 2 → 1. Brand scope 6/6, negatives 2/2,
development probes 7/16 (top1 4/16) без изменений; ошибок исполнения 0.
Это development-результат, не доказательство улучшения на новом независимом наборе.
Сводка/диагностика: [identity-ranking-development-v1.json](../testdata/evaluation/identity-ranking-development-v1.json).
Полные отчёты локально artifacts/quality-before/after-{tuning,probes}.json;
их SHA сохранены в сводке. Старый holdout после изменения не запускался.

Score приоритетных результатов: 1 + 1/(60 + lexical identity rank),
остальные сохраняют RRF score. Это ранговый балл, не вероятность релевантности;
IdentityFamilies — количество совпадений во всём lexical candidate list.
Список формируется до итогового limit, чтобы совпадение не потерялось при RRF.
Фильтры, цены, роль SKU и финальная application-валидация не ослаблены.

Следующий цикл: устранение потерь task retrieval на development, проверка
доступных SKU трёх кандидатов и новый независимый набор перед сравнением.
Нельзя объявлять это исправление достаточным для четырёх релевантных товаров.
