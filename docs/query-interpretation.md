# Выборочная интерпретация запроса

Контракт и выборочный порт подключены к [бюджетируемому адаптеру](query-parser-runtime.md).
По умолчанию parser выключен; `-parser-mode replay` читает кэш, `live` явно
разрешает платную попытку. Обычная CLI без этого флага сохраняет прежнее поведение.

## Отбор

После BM25 вызываем настроенный parser только при пустой лексической выдаче,
не менее пяти словах, без точного артикула, limit_reason, известного семейства
или уже распознанного именованного намерения. Это начальная development-политика,
не измеренный оптимум. Запросы с неподдерживаемыми ограничениями останавливает
общий lexical use case до этого шага.

## Контракт interpretation-v1

Ответ: version, source_query (точная копия исходного запроса), status
(`resolved`, `clarify`, `unsupported`) и semantic_query. Для resolved текст
непустой, максимум 256 символов; для остальных статусов он пустой.
Запрещены управляющие символы, неверный UTF-8 и изменение последовательности
токенов с цифрами. JSON ограничен 4096 байтами: неизвестные/повторные ключи,
null, недостающие поля, лишние JSON-значения и markdown-обёртки отклоняются.
Сообщения об ошибках не включают сырой ответ или секреты провайдера.

В схеме нет товарных ID, цен, фильтров или признака совместимости. Валидная
интерпретация — поисковая гипотеза, а не доказательство соответствия товара.
Исходный запрос, query plan и все детерминированные SKU-фильтры сохраняются;
текст используется только как вход вектора. Resolve получает исходный Request.
Финальная выдача проходит прежний lexical.Search и его проверку SKU.

При ошибке parser/валидации используем исходный векторный запрос; при clarify
или unsupported не запускаем векторы, отражаем статус в trace. Отмена запроса
прерывает работу. Текст переписывается максимум один раз, без рекурсивных вызовов.

## Проверка и следующий шаг

Unit-тесты проверяют отбор, неизменность запроса/ограничений, три статуса,
невалидный ответ, ошибки и отмену. JSON-декодер проверяется отдельно от сети.
Ни tuning/holdout, ни товарные цели не поступают в parser.

Версии prompt/model, общий ledger $5, кэш, защита неизвестных исходов и replay
реализованы в parser runtime. Оценка полного development-запуска — отдельный
план перед сетью; массовая отправка каталога в LLM не требуется. До измерения
нельзя заявлять исправление SNMP вместо удалённой помощи, рост Hit@4 или
завершение всего разбора сложных условий.
