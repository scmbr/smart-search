# Лексический поиск: lexical-v3

Целевой путь: активный PostgreSQL-снимок → Elasticsearch → CLI search.
Статус: domain/application, адаптеры и CLI реализованы; unit/HTTP/реальные
PostgreSQL/Elasticsearch-тесты проходят. Полный feed проиндексирован и проверен.
Публичный HTTP API, рекомендации/verifier и интерфейс — следующие части MVP.
Этот шаг не расходует OpenAI API и не подбирает параметры по holdout.
Правила опечаток query-v1 описаны в [query-normalization.md](query-normalization.md).
Новые [условия query-v2](query-constraints.md) используют characteristics-v3 /
lexical-v3 и требуют нового снимка/индекса. Устаревшая схема возвращает not ready.
Для воспроизводимости выдачи CLI показывает также версию query policy.

## Подготовка индекса

- Источник фиксируется по ID готового снимка с текущей политикой характеристик.
  Категории читаются в память, предложения — порциями с keyset по ordinal.
- Версия индекса включает snapshot ID, схему документа и SHA-256 маппинга семейств.
  Индекс строится под собственным именем; одна index-сессия держит PostgreSQL advisory lock.
- Повтор staging перезаписывает те же ID теми же документами; повтор ready проверяет
  число документов. Старый индекс не удаляется. Ошибка bulk/счётчиков не меняет alias.
- После refresh/count индекс получает write block и метаданные ready. Если активный
  каталог уже сменился к финальной проверке, активация отменяется. Замена search alias атомарна.
  PostgreSQL/ES не образуют общую транзакцию: выдача может использовать целый
  предыдущий снимок, но не смешивает товары и метаданные разных индексов.
- Поиск разрешает alias в физический индекс, читает его метаданные и ищет именно
  в нём: смена alias не смешивает catalog/index versions внутри ответа.

## Семейства

Версионированный конфиг задаёт family ID, несколько group IDs, vendor path и источник.
Правила используют структуру feed и исходные целевые страницы; это предварительная
ручная разметка, а не независимая оценка качества. Разные версии/лицензии одной группы
не становятся разными семействами. Поддержка и полная лицензия остаются разными SKU.
Неразмеченные группы получают provisional key и family_confirmed=false. Без группы
ключ привязан к offer ID. Такие ключи не доказывают четыре разных семейства.
Нормализация неизвестных семейств по похожему названию не выполняется.

## Поиск

BM25: отдельное имя продуктового узла из дерева feed, название/артикул/категории
имеют больший вес, чем ограниченное описание. ProductName берётся по исходному
group ID, если узел существует; это поисковый текст, не доказательство семейства.
Исторически query-v1: ProductName=24; в query-v2 вес повышен до 64
после regression-проверки с расширенным каталогом SKU. Name=8, FamilyName=4, VendorCode=12, Vendor=2, CategoryNames=3,
Description=1. Иначе ПО, которое упоминает платформу в длинном SKU, может вытеснить ОС.
Reader v2 поддерживает старую схему v1 на время пересборки; новое поле аддитивно.
Анализатор разделяет CamelCase, сохраняет исходные токены, приводит регистр/ё и
применяет русский stemming. Ввод передаётся как текст, не как query_string DSL.
Фильтры характеристик применяются до collapse и к конкретному SKU.
Явные версии КриптоПро CSP/Astra Linux и роль запроса разбираются существующими
консервативными правилами. Остальные числа не превращаются в version filter.
Для точного общего «сервер» приоритет задан аппаратному типу; «ПО для сервера» — софту.

Без явного запроса продления/обновления/поддержки такие роли исключаются;
конфликтная роль не используется как прямое совпадение. Unknown остаётся unknown.
priced_first сначала ищет релевантные положительные цены, затем при полном
отсутствии таких совпадений — неизвестную цену с флагом fallback. available_only
строго исключает available=false. Релевантность предшествует цене и наличию.

Collapse по family key возвращает один подходящий SKU на группу. Счётчик ES hits
не выдаётся за число уникальных семейств. CLI показывает до limit карточек,
подтверждённость группировки и shortfall при нехватке четырёх подтверждённых семейств.
Случайные товары для дополнения четвёрки не добавляются.

## Приёмка

До реализации: domain-тесты resolver/query/document, application-тесты порций,
сбоев и активации; HTTP-тесты DSL/bulk/error handling. Реальный Elasticsearch:
порядок «сервер»/«ПО для сервера», exact SKU, версия CSP, фильтры до collapse,
priced/unpriced fallback, разные семейства, повтор индексации и отказ активации.
Исходные 10 запросов используются только как reference smoke; успехи и промахи
фиксируются, не объявляются независимой точностью или ростом конверсии.

## Команды

```powershell
docker compose --profile search up -d --wait postgres elasticsearch
go run ./cmd/catalog-index
go run ./cmd/search -query "КриптоПро CSP 5.0"
go run ./cmd/search -query "сервер"
$env:TEST_POSTGRES_DSN = 'postgres://smart_search:smart_search_local@127.0.0.1:5432/smart_search?sslmode=disable'
$env:TEST_ELASTICSEARCH_URL = 'http://localhost:9200'
go test -count=1 -v ./internal/infrastructure/...
```

Нужны .env и ранее выполненный catalog-import. Индексация читает PostgreSQL;
повторно копировать исходный feed не требуется. Сервис поиска читает физический
индекс с метаданными; Elasticsearch API key при наличии используется только backend.
Результат CLI — отладочный контракт baseline, не реализация docs/openapi.yaml.
Нужен запас места для Docker-образа/индекса/Go-кэшей; перед первым запуском —
не менее 10 ГБ свободного диска, контейнер ES ограничен 2 ГБ RAM/2 CPU, heap=512 МБ.

Для машины с 16 ГБ RAM и работающими пользовательскими приложениями проверки
лучше запускать последовательно, после окончания индексации:

```powershell
$env:GOMAXPROCS = '2'
$env:GOMEMLIMIT = '512MiB'
go test -p 1 -count=1 ./...
```

## Проверенный прогон 2026-11-27

Ниже сохранён исторический прогон с families-v1. Текущий маппинг families-v2
объединяет две редакции Кибер Бэкап; evidence и ограничения оценки описаны в
[evaluation-review.md](evaluation-review.md). Для нового маппинга нужно повторить
catalog-index: его fingerprint входит в имя индекса, старый индекс не переписывается.

Индекс lexical-v2 содержит 136 040 документов активного снимка
9895c5265cb9360c0a8c5c2eec6bd890e528687c9a903da7055d3d219aeaf50e.
Сборка заняла 155,967 с; повтор — 104 мс, Reused=true без повторной записи.
Сохранён и предыдущий индекс lexical-v1. Первый прогон v1 дал 7/10 контрольных
целей: выявил проблему совместимого ПО выше самого продукта. Поле ProductName
и приоритет каталожного имени исправлены общим правилом; regression-тест проходит.

Воспроизведение исходных запросов:

```powershell
go build -o bin/search.exe ./cmd/search
python scripts/evaluate-reference.py --output artifacts/reference-baseline-v2.json
```

Итог reference smoke: 9/10 контрольных целей в топ-4, ошибок выполнения 0.
Из них 7/8 целей с явно размеченным семейством и 2/2 широких vendor/category целей.
Последние не считаются проверенными наборами семейств; это не независимый Family Hit@4.
«365» остаётся неоднозначным: Microsoft 365 Family — на позиции 4, без принудительной
подмены остальных продуктов. В целевой группе MaxPatrol EPP найдено 6 продлений
и 0 новых лицензий: общий запрос пустой, явный -kind renewal проверяется отдельно.

На исходных 10 запросах FourFamiliesConfirmed=false: покрытие маппинга ограничено,
а рекомендации/verifier ещё не реализованы. Требование четырёх разных семейств
пока не выполнено. SKU-eligibility, архитектура выбранного варианта и независимая
релевантность этим smoke не доказаны. Результаты, конфиги прогонов и длительности
CLI (включая старт процесса) сохранены локально в artifacts, не в Git.
