# Роль предложения в поиске

SDD, product-role-v1 / lexical-v6 / query-v5. Роль лицензии new/renewal/support
недостаточна: full может означать лицензию компонента, а не основного продукта.

## Политика

Индекс сохраняет ProductRole, ProductRoleRule, ProductRoleSource и ProductRoleText.
Роли: library, addon, media, service, support; пустое значение — unknown,
а не подтверждение полноценного самостоятельного продукта.

Сильные сигналы: идентичность названия SKU/группы; точное значение «Тип лицензии»
в описании feed; leaf-категория библиотек для разработчиков/сервиса. Упоминание
библиотек, поддержки или функций в обычном описании не является ролью товара.
Лицензия с включённой поддержкой/дистрибутивом не равна отдельной услуге/носителю.
Две библиотеки проверены дополнительно: vendor path + group_id, источники ниже.
Точное значение типа лицензии имеет приоритет; далее эвристики идентичности:
media → support → service → addon → library. Правило и исходный
фрагмент сохраняются; price/available/семейство не используются для вывода роли.

Без запроса зависимой позиции исключаем известные library/addon/media/service/support.
Явно запрошенные SDK/библиотека, дополнение, носитель или услуга получают строгий
role-фильтр: unknown не удовлетворяет ему. Запрос поддержки сохраняет прежний
Kind=support и разрешает соответствующую роль, не ослабляя лицензионный фильтр.
Отрицание «не библиотека» не разрешает библиотеки. Неоднозначный запрос нескольких
ролей не интерпретируется как одна из них. Точный однословный числовой SKU/артикул
может искать зависимую позицию; остальные строгие условия сохраняются.
Для двух проверенных библиотек точные именованные запросы GoDiagram/Northwoods
и Aspose.Diagram/Aspose также разрешают library, сохраняя остальные ограничения.
Иначе фильтр скрыл бы явно названный продукт. На неназванные задачи эти исключения
не распространяются; это не буст бренда и не маппинг цели из evaluation.

ProductType=software выводится только из явной начальной именной фразы пользователя
(например, «офисные приложения», «защищённая российская операционная система»).
«Сервер для программного обеспечения» не превращается в запрос ПО. Модель не меняет
роль или тип. Для остальных свободных задач неизвестное назначение остаётся неизвестным.
В QueryPlan выводятся версия ролевой политики, запрошенная роль и исключённые роли.

Ролевые фильтры одинаковы в BM25 exact/expanded, в priced/unpriced и vector Resolve;
работают до collapse FamilyID. Application повторяет классификацию выбранного SKU,
сверяет сохранённую роль/evidence и отклоняет обход фильтра. Оставшиеся места не
заполняются случайными товарами. Unknown допускается в общем поиске без обещания
соответствия задаче; это ещё не verifier релевантности или совместимости всех top4.

## Приёмка

Сначала unit-тесты классификации, evidence, отрицаний/явных ролей, точного SKU,
неизвестного и включённых сервисов. Затем application-тест отказа backend, обошедшего
правило; real ES: неподходящий SKU в том же семействе не скрывает основной,
явная библиотека/носитель доступны, unpriced не обходят фильтр. Полный индекс,
повтор без записи и cache-only tuning/probes; holdout не запускается.

Для локального прогона в PowerShell перед `go run ./cmd/catalog-index`:
`$env:PGOPTIONS = '-c max_parallel_workers_per_gather=0 -c jit=off'`.
Первый запуск без этих настроек превысил 30 с на чтении категорий; alias остался
на прежнем lexical-v5. Повтор использует тот же снимок, тайм-аут не увеличивается.

## Проверенный файловый источник

Повторный PostgreSQL-прогон остановился на 56 000 предложений при чтении порции.
Контрольный EXPLAIN ANALYZE с материализацией JSON: 6.194 с на 500 строк, из них
6.140 с — I/O. План использовал (snapshot_id, ordinal), повторного полного scan
не было. Прогрев последних 512 МиБ TOAST через pg_prewarm: prefetch завершился,
синхронный read превысил ограничение 180 с. Приложению pg_prewarm не требуется.

Для такого локального I/O добавлена реальная команда:

```powershell
go run ./cmd/catalog-index -local-feed <путь-к-исходному-feed>
```

Без флага остаётся прежний PostgreSQL-источник. С флагом читается оригинальный
XML/gzip, а не выгрузка новых или изменённых товаров. До подготовки индекса:

1. Зафиксировать ready snapshot и удерживать прежний index advisory lock.
2. Сделать приватную копию feed с SHA; полная identity должна совпасть с active ID:
   содержимое, текущая normalization и reader limits (1 МиБ / 1 ГиБ / 100 issues).
3. Полностью провалидировать поток, сравнить число категорий/предложений с metadata.
   Нормализовать тем же domain.Normalize, сохранить минимальные строки в приватный
   временный spool максимум 4 ГиБ. Тяжёлые raw-поля/evidence отбрасываются только
   в этом кэше; PostgreSQL и доказательства в исходном каталоге не меняются.
4. Передать строки существующему BuildDocument. Проверить полный count/current
   snapshot перед активацией; при ошибке новый alias не включается.

Тест доказывает равенство итоговых Document с обычным PostgreSQL-путём, отказ при
другом SHA и поздней ошибке XML, очистку файлов/освобождение блокировки. Чтение
приватного feed буферизовано по 128 КиБ. После закрытия исходная копия и spool
удаляются. Source mode выводится в CLI-отчёте и не меняет fingerprint: документы
имеют ту же семантику, тот же snapshot ID и индексную схему.
