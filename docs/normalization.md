# Характеристики предложений: characteristics-v5

Основание: R-03, T-07/T-07a, D-018. Нормализация детерминирована, без LLM и сети.
Вход — один Offer: параметры, название и тип продукта. Данные соседних SKU,
source group ID, категория, цена и description не доказывают характеристики.

## Результат

Каждый признак имеет status=known/unknown/conflict, значение, reason и evidence:
вид источника (parameter/title), имя поля, raw value, индекс параметра и rule ID.
При unknown/conflict значение пустое: downstream не может использовать удобную
часть противоречивых данных. Это извлечение признаков, а не проверка совместимости.

- product_type: software/hardware только из «Тип продукта».
- offer_kind: new_license/renewal/upgrade/support; иначе unknown.
  Точные значения «Полная версия»/Full, «Продление», «Обновление»/«Перекрестное
  обновление», «Техподдержка»/«Техническая поддержка» задают роль. Подписка, модуль,
  базовая лицензия и расширение сами по себе не доказывают новую лицензию.
- license_type: нормализованный тип из закрытого словаря «Тип лицензии»;
  не смешивается с моделью лицензирования. Подписка может быть продлением.
- delivery_method: ESD вынесен в отдельный признак со своим evidence; он не
  противоречит Full/Renewal и сам по себе не доказывает роль/право покупки.
- version: числовое значение из параметра «Версия» либо узкого правила названия
  для КриптоПро CSP/Astra Linux и явных заголовков Microsoft Office с годом версии. Номер сохраняется точно, не берётся из артикула,
  срока, количества пользователей или произвольного числа в названии.
  Для апгрейдов/миграций и названий с переходом между версиями значение берётся
  только из параметра: число в названии может обозначать исходную версию.
- edition: Standard, Enterprise и другие явно перечисленные редакции из поля
  «Версия»/«Редакция» и ограниченных явных названий SKU; они не становятся технической версией. Неизвестные редакции не угадываются.
  Для Microsoft 365 поддержаны явные Personal/Персональный и Family/для семьи
  того же SKU; число 365 не является версией.
- platforms: только явный список ОС из «Платформа»/«Совместимые платформы».
  PC/Mac и установленная «Операционная система» оборудования не доказывают ОС
  совместимости. Архитектура x86-64 не означает Windows или Linux.
- architectures: x86_64/arm64/elbrus_vliw из явного поля архитектуры.
- users_limit/nodes: положительное целое до 1 000 000, только из полей с соответствующей
  семантикой; users_limit также из явного «на N пользователей» в названии того же SKU.
  Ноль/000, диапазоны, дроби, безлимит и неверные единицы дают unknown.
  Пользователи и узлы не взаимозаменяемы; верхняя граница пользователей не доказывает
  применимость лицензии к организации или права покупки.
- devices_limit/ip_addresses_limit/participants_limit: отдельные верхние границы
  из явных фраз названия SKU, до 1 000 000. Число узлов не становится числом IP.
  Диапазоны/отрицания и смешанные единицы не доказывают ёмкость; разные значения
  одного типа дают conflict. Неизвестное значение не заменяется соседней ёмкостью.

Текстовые значения сравниваются после trim, схлопывания пробелов, lower-case и ё→е.
Маркеры неизвестности и Parameter.Known=false не становятся известными значениями.
Повтор одинакового scalar допустим; разные известные scalar или противоположные
сигналы роли в параметре/названии дают conflict. Частично непонятный scalar также
не считается достоверным. Множественные платформы/архитектуры объединяются только
при распознавании всех значений. Пустые маркеры не отменяют явное известное значение.

Для роли название даёт только ограниченные явные сигналы: новая лицензия, продление,
upgrade, сертификат/отдельная техническая поддержка. «Лицензия с технической поддержкой»
не превращается в отдельную поддержку. Роли из названия не извлекаются для hardware.
Числовые версии из названия имеют evidence=title: будущий verifier не должен считать
их доказательством совместимости с другой ОС/версией без применимой политики.

## Сохранение и версии

Application импорта вычисляет Characteristics перед записью, игнорируя переданное
готовое значение. Raw параметры не изменяются. Номер политики добавляется в identity
снимка: прежние ready-снимки неизменны, новая политика создаёт новый снимок при том
же SHA-256 feed. При resume используется та же политика; повышение версии запрещает
смешивание уже записанного префикса с новыми правилами. Структура JSONB расширяется
аддитивно; SQL-миграция для неё не нужна. Старый active остаётся до успешного импорта.

## Приёмка

Unit-тесты до реализации: full/renewal/upgrade/support, подписка и add-on,
конфликт названия и параметра, несколько редакций, версия из разрешённого названия,
числа пользователей/дат/артикулов не становятся версией, архитектура не становится ОС,
нет наследования между SKU, неизвестные значения/единицы/диапазоны, стабильность
evidence и отсутствие изменения исходных данных. Application-тест проверяет
версию identity и замену недоверенного готового результата; PostgreSQL-тест — round trip.

Локальная проба v1 выявила неоднозначность версии в названиях апгрейдов.
Политика v2 закрывает её; снимок v1 сохраняется как исторический, повторно не активируется
при загрузке v2. Unknown числового признака требует проверки status; его Value=0 —
нулевое значение Go, а не утверждение о ёмкости лицензии.

## Расширение characteristics-v4

DevicesLimit, IPAddressesLimit и ParticipantsLimit — независимые поля с единицами
devices / ip_addresses / participants. Извлечение — только из явных фраз того же
SKU; неизвестная ёмкость/диапазон/конфликт не экспортируются в строгие поля поиска.
Числа вне 1..1 000 000 не становятся известной ёмкостью. Правила дополнены
назначением серверной лицензии/рабочего места и подтверждённым названием Office
Home 2024; [ограничения и источник](query-constraints.md).
