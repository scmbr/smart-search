## 100 активных кейсов

Подготовлены синтетические запросы по предоставленному каталогу, не реальные логи:
**60 tuning + 40 holdout**, версия evaluation-v3. Удобная таблица со всеми
запросами, названиями групп, ссылками и ограничениями —
[evaluation-cases.md](evaluation-cases.md). Замечания принимаются по ID строки.

- [scenarios.json](../testdata/evaluation/scenarios.json): 60 кейсов настройки,
  9 брендов. Включены исходные семейства, точные названия/SKU, опечатки,
  транслитерация, сленг, задачи, версии, лицензии, наличие и два отрицательных случая.
- [holdout-v2.json](../testdata/evaluation/holdout-v2.json): 40 кейсов по брендам
  Adobe, TrueConf, Dr.Web и UserGate, отделённым целиком от настройки. Исходные
  восемь запросов сохранены, добавлены другие варианты и продукты этих брендов.
  Хэши запросов/ожиданий и определений семейств зафиксированы до просмотра выдачи.
  Поиск по holdout не запускался, независимая разметка не подтверждена.
- [regression-v1.json](../testdata/evaluation/regression-v1.json): прежние
  10 сценариев с original_split и раскрытым holdout. Они сохранены как история
  разработки, не входят в активные 100. Десять исходных Excel reference smoke
  также остаются отдельно и не являются независимым holdout.

В обоих наборах представлены разные типы запросов. Все семейства, опечатки,
алиасы и широкие запросы одного бренда остаются на одной стороне. brand_id —
ключ vendor scope снимка (например, entensys для UserGate), названия для человека
показаны в таблице. Сущности families — предварительные цели оценки, а не
автоматически принятые production-правила группировки.

Весь каталог, включая товары holdout, может участвовать в обычной индексации.
Отложенными остаются запросы и суждения о релевантности; по их результатам
нельзя подбирать правила ранжирования до независимого измерения.

Широкие запросы («адоб», «доктор веб», «майкрософт») имеют target_scope=brand:
список семейств/групп — примеры, не исчерпывающая разметка. Допустим просмотр
продуктов бренда или уточнение; нельзя требовать одну заранее выбранную карточку
или считать другие продукты этого бренда ошибкой. Такие строки не являются
эталоном Family Hit/Precision/nDCG. Для полной оценки релевантности нужны
исчерпывающие/градуированные суждения, которые пока отсутствуют.

Условия лицензии хранятся отдельно от семейства. Если характеристика SKU
неизвестна, нельзя объявлять её подходящей. Ссылка на пример предложения лишь
подтверждает наличие группы; это не обещание, что этот SKU подходит запросу.
Эти 100 примеров не доказывают покрытие всего каталога или качество рекомендаций.

Воспроизведение проверок без поиска/OpenAI:

```powershell
python scripts/audit-evaluation.py --feed "C:/Users/hypoc/Downloads/Mindbox.yml.gz.xml"
python scripts/render-evaluation.py --check
go test ./contracts
```

Аудит сверяет SHA feed, названия, counts, примеры и vendor scope 33 групп.
Он проверяет факты каталога, а не правильность смыслового сопоставления.
Скрипт render-evaluation.py обновляет таблицу по JSON; --check включён в CI.
Правка JSON не обновляет хэши автоматически: изменения целей требуют явной
проверки версии/истории использования набора до следующего замораживания.

## Поведенческие проверки baseline

- Domain: конфликтующие определения одного family_id отклоняются; разные группы
  с согласованным определением объединяются. Новый тест сначала воспроизвёл
  ошибку, затем прошёл после исправления NewFamilies.
- Application: неизвестная/недостаточная ёмкость и платформа, неподходящая версия,
  продление/upgrade без явного запроса, конфликт роли, недоступность, смешение
  ценовых слоёв и повтор SKU не проходят в выдачу. Пустой ответ не дополняется
  случайными товарами; флаг четырёх семейств пересчитывается, ошибки не маскируются.
- Elasticsearch: две группы одного семейства дают одну карточку; версии,
  категории, артикулы и запасной слой проверяются реальным интеграционным тестом.

Тесты опечаток/синонимов, контекста, RRF и verifier добавляются до реализации
соответствующих функций этапов 3–4. Тесты baseline не закрывают эти функции.

## Что требуется для независимой оценки

1. Проверить подготовленные draft запросы и семейства, не использованные в настройке/выборе правил.
   Рецензент фиксирует ожидаемые семейства, допустимые варианты, запреты и причины
   до просмотра поисковой выдачи. Исходные vendor/category цели требуют явных
   допустимых семейств; широкий vendor hit не считается Family Hit@4.
2. Отдельно проверить разметку по снимку/доказательствам: сохранить дату, автора
   независимой проверки, решения по спорным случаям; сейчас этот статус pending.
3. Заморозить версию/хэш набора, затем измерить baseline и будущий гибридный поиск
   одинаковым способом. Не менять ожидаемые ответы по результатам неудачного прогона.
4. После использования набора для настройки перевести его в regression и заменить
   holdout. Не заявлять Precision/nDCG без полной/градуированной разметки.
