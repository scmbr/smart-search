# Снимки каталога в PostgreSQL

Контракт этапа 2. Импорт не строит поисковый индекс и не расходует OpenAI API.

Реализация: internal/domain/catalog, internal/application/catalogimport,
internal/infrastructure/feed и internal/infrastructure/postgres; composition root —
cmd/catalog-import. Команды запуска и интеграционных тестов — в [README](../README.md).

- Перед импортом локальный файл копируется потоком в приватный временный файл.
  SHA-256 вычисляется по скопированным исходным байтам, включая gzip-обёртку.
  Reader читает эту копию; изменение оригинала во время импорта не меняет снимок.
  Копия удаляется при штатном выходе. Нужен дополнительный диск размером с feed.
- Идентичность снимка: SHA-256 от версии нормализации/лимитов и SHA-256 источника.
  Иной источник или версия создают новый снимок. Путь файла не входит в ключ.
- Состояния: staging → ready либо invalid. Один writer на БД удерживает session
  advisory lock; конкурентный импорт возвращает понятную ошибку занятости.
- Категории и предложения записываются порциями. Записи и общий порядковый
  checkpoint фиксируются одной транзакцией. Незавершённая порция откатывается.
- После прерывания повторно читается весь неизменный источник: reader заново
  проверяет XML, дубли и gzip checksum, а уже зафиксированный префикс не пишется.
  Это возобновление записи, не быстрый seek внутри XML/gzip.
- Только полный отчёт без диагностик, с непустым каталогом и совпадающими
  счётчиками сохранённых записей разрешает ready. Статус и active pointer меняются
  одной транзакцией. Поздняя ошибка никогда не заменяет предыдущий active.
- Завершённый невалидный источник получает invalid и не активируется. Ошибка
  чтения/БД/отмена оставляет staging для повторения. Invalid — терминальное состояние.
- Повтор ready возвращает тот же ID без записи и без повторной активации:
  повтор старого источника не откатывает более свежий активный снимок.
- Активный снимок БД — проверенные исходные данные; готовность поискового индекса
  проверяется отдельно. Старые снимки автоматически не удаляются.

Приёмка: unit-тесты правил domain и orchestration application; PostgreSQL-тесты
атомарных порций, checkpoint/retry, блокировки, миграций, late failure и идемпотентности.
Обычные go test работают без БД; интеграционные тесты включаются отдельным DSN.

Миграция 001 создаёт catalog_snapshots, catalog_records и catalog_active. Записи
изолированы snapshot_id, содержат source ID, порядковый номер, вид записи и JSONB
полного нормализованного содержимого (включая raw поля). Это staging-формат,
а не схема API или готовая модель поиска. Schema version меняется вместе с
маппингом reader/domain/persistence. Родители категорий, цены и ссылки проверяются
reader перед ready; SQL ограничивает ID, уникальность и ссылку на снимок.

Пароль Compose предназначен для локального демо; порт привязан к 127.0.0.1.
CLI ограничивает подключение 5 секундами, SQL statement — 30 секундами;
транзакция одной порции короче полного импорта. Отмена контекста прерывает работу.

## Проверенный прогон

2026-11-26, Windows/Go 1.27.3, Docker 29.9.3, PostgreSQL 17.12: импорт исходного
файла 291 988 701 байт записал 9 311 категорий и 136 040 предложений за 146,201 с.
Checkpoint=145351, rejected=0, issues=0, статус ready. SHA-256 снимка совпал с
исходным файлом. Время включает подготовку временной копии и сохранение в БД.
Повтор занял 22,220 с (включая копирование/хэширование), вернул тот же ID и Reused=true.
Локальные отчёты: artifacts/catalog-import.json и artifacts/catalog-import-repeat.json.

Реальные PostgreSQL-тесты подтвердили откат порции с дублем, сохранение checkpoint,
возобновление после прерывания, блокировку второго writer, повтор миграций и
проверку checksum, сохранение active при invalid/поздней ошибке XML и отсутствие
отката на старый ready-снимок. Это проверка импорта; качество поиска не измерено.
