# Программная проверка допродаж

Основание: уточнение экспертов №7, R-07, D-018.
Цель — проверять характеристики и лицензирование конкретной пары предложений,
а не считать ссылку или текст модели достаточным доказательством.

## Вход

anchor_offer_id, recommended_offer_id, версия каталога, нормализованные характеристики
обоих SKU, контекст покупателя и применимая версия политики policy_id. Источники
характеристик — feed или заранее проверенные материалы вендора с областью действия.
Текстовое упоминание платформы в описании не равно подтверждённой поддержке.
Исходная нормализация [characteristics-v1](normalization.md) уже сохраняет status
и evidence. Извлечённые из названия версии не считаются автоматически доказательством
совместимости; неизвестные и конфликтные признаки требуют unknown в будущем verifier.

Политика заранее задаёт обязательные проверки для типа связи; кандидат/LLM не может
удалить неудобное правило или выбрать только одно успешное. Для разных категорий
набор различается: платформа и версия, архитектура, лицензия, число пользователей
или узлов, тип организации. Правило с неприменимым источником считается unknown.

## Правила

- equals: равенство нормализованных идентификаторов/значений.
- contains: принадлежность явно подтверждённому списку поддерживаемых платформ/версий,
  не произвольный поиск подстроки в описании.
- at_least: числовая проверка ёмкости лицензии после строгого разбора единиц.
  «Неизвестно» и число в другой единице не превращаются в ноль или успех.
- license_eligible: допустимость покупки новой лицензии/продления/обновления для
  явно заданного контекста. Отсутствие сведений о праве продления — unknown.

Используется закрытый набор операторов; внешние источники не передают исполняемый код.
Преобразование значений и синонимов характеристик версионируется. Противоречивые
данные не выбираются по удобству: результат unknown с диагностикой конфликта.

## Результат и публикация

Каждое обязательное правило даёт passed, failed или unknown с наблюдаемым значением,
ожиданием и источником. Общий passed допустим только при полном покрытии обязательных
правил и passed для каждого. failed/unknown не допускаются в recommendations/top4
как подтверждённая допродажа. Отказы и неизвестные значения доступны в trace.

Положительный отчёт verification включает policy_id, оба offer ID, checked_at
и checks. Backend проверяет, что отчёт относится к выбранным SKU/снимку и полной
политике, а не другому варианту лицензии. Смена SKU, версии, контекста, политики
или исходных характеристик инвалидирует кэш результата проверки.

LLM может предложить связь и извлечь кандидатов значений, но не назначает passed.
Для демонстрационных fixtures используются вымышленные источники с явной пометкой;
их прохождение схемы не доказывает реальную совместимость товаров Softline.

## Граница первой реализации

Domain `verification` проверяет закрытые операторы; application загружает политику
и факты через доверенный порт, а не из тела запроса или ответа LLM. Политика содержит
непустой полный список обязательных правил с уникальными ID. Запрос выбирает только
policy_id и пару SKU; свой набор правил передать нельзя. Контекст содержит явные
проверенные права покупателя; отсутствие права — unknown, явный запрет — failed.

Факт содержит status, значения либо целое число с единицей, идентификатор источника
и область SKU/снимка. Только подтверждённый структурированный факт применимого
источника допустим; название/описание сами по себе не являются подтверждением.
Для equals/contains слева — факт anchor, справа — recommended; at_least проверяет
ёмкость recommended >= потребности anchor в одинаковой непустой единице.
Число применимо только с NumberKnown=true; отсутствие числа не равно нулю.
license_eligible сопоставляет явный тип покупки recommended с подтверждённым правом
контекста. Никаких преобразований единиц и извлечения правил из произвольного текста.

Отчёт содержит SHA-256 всех входов (полная политика, факты, контекст, SKU и снимок).
Перед публикацией он проверяется повторным расчётом; изменение даже при сохранении
policy_id инвалидирует отчёт. Это проверка согласованности, не криптографическая
подпись: публичные API не должны принимать отчёты от клиента.

Реализовано: `internal/domain/verification`, `internal/application/verification`.
Повторение unit-тестов: `go test ./internal/domain/verification ./internal/application/verification`.
Контекст загружается по серверному ContextID; application отклоняет подмену ID
политики, SKU, снимка или контекста. Источник обязан предоставлять полную политику.

Первый шаг не подключает verifier к HTTP, не добавляет vendor scraping и не объявляет
реальные пары совместимыми. Продуктовые политики и адаптер подтверждённых фактов,
затем рекомендации и интеграционные сценарии остаются отдельными задачами этапа 4.

## Поведенческие тесты

Совпавшие platform/version и допустимая лицензия; несовпавшая версия; неизвестная
платформа; превышение числа пользователей; нет права продления; противоречивые
источники; неполный набор обязательных правил; подмена offer ID или policy_id;
перенос отчёта между версиями каталога; инструкция внутри недоверенного источника.
