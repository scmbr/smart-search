# Архитектура

Статус: базовый вариант; см. D-004–D-010 и открытые решения.

## Компоненты

- React + TypeScript + Vite: интерфейс покупателя, аналитика и разбор запроса.
- Go backend: HTTP API на net/http, продуктовая логика, команды импорта и индексации.
- PostgreSQL через pgx: исходные и нормализованные данные, источники, события.
- Elasticsearch через официальный клиент: лексический индекс, векторы и подсказки.
- OpenAI через официальный Go SDK: эмбеддинги и выборочный разбор сложных запросов.
- Docker Compose: воспроизводимое окружение; версии фиксируются до реализации.

Приложение — модульный монолит. Модули каталога, поиска, рекомендаций и аналитики
имеют явные границы. Продуктовая логика не зависит от SDK внешних сервисов.
Не вводим отдельные микросервисы, брокер и Redis без подтверждённой необходимости.
Агентный цикл не обязателен. Модуль рекомендаций включает программный verifier
характеристик/лицензий конкретной пары SKU; без положительного отчёта допродажа
не публикуется. Сервис нормализации семейств отделяет family_id от source group_id.
Аналитика — выбранная бонусная функция по последним уточнениям экспертов.

## Два пути работы

Подготовка: потоковый feed → валидация и PostgreSQL → продуктовые группы →
поисковые документы → эмбеддинги → индекс Elasticsearch → проверка → активация.

Поиск: запрос и контекст → нормализация → кандидаты BM25/векторы → RRF →
проверка ограничений → группировка → предложения и рекомендации → ответ и событие.

Версия индекса связана со снимком каталога, схемой документа, моделью и размерностью
эмбеддингов. Индекс активируется только после проверки. Прерванная сборка не
подменяет активный индекс. Сохраняется возможность отката на предыдущую версию.
Группа не означает одну версию или один тип лицензии. Отбор конкретных предложений
учитывает роль (новая лицензия/продление/обновление/поддержка), платформу и ограничения.
Явные фильтры по возможности применяются при получении кандидатов и повторно
проверяются при выборе предложения, чтобы постфильтрация не теряла релевантные товары.

## Ограничения ресурсов и стоимость

XML читается последовательно; запись в БД и Elasticsearch выполняется порциями.
Для OpenAI и индексации используются ограниченные worker pools и backpressure.
Повторы ограничены по числу и времени, учитывают Retry-After и не дублируют запись.

Вектор пересчитывается при изменении поискового текста, модели или схемы подготовки.
Цены и наличие должны обновляться без обязательного пересчёта смыслового вектора.
Кэш учитывает запрос, фильтры, контекст, версии индекса/модели; история разных
сессий не смешивается. Полная индексация начинается после оценки расходов на выборке.

Метрики: длительность этапов, p50/p95, число API-вызовов, токены, фактическая
стоимость, попадания в кэш, повторы и ошибки. Стоимость подготовки и запроса раздельны.

## Отказы и доверие

При недоступности OpenAI используем BM25 и локальную нормализацию, сообщаем
ограниченный режим. При недоступности Elasticsearch возвращаем явную временную
ошибку, не выдаём отсутствие инфраструктуры за отсутствие товаров.
Недоставленные события аналитики сохраняются в ограниченном механизме повторов;
потери видимы, идентификаторы защищают от повторного учёта.

Пользовательский ввод и тексты источников недоверенные. Backend проверяет ответ
модели, разрешённые поля/значения и наличие product/offer IDs. Ключ OpenAI
доступен только backend. Внешние ссылки допускают только безопасные схемы;
сырой HTML описаний не выводится без обработки.
