# Обработка запросов query-v1

Историческая политика query-v1; текущая query-v4 добавляет [условия](query-constraints.md)
и [именованные задачи](freeform-queries.md).
Первый шаг этапа 3: расширение лексического поиска без OpenAI и без изменения
индекса/разметки holdout. Это не векторный поиск и не полный разбор условий лицензий.

## Поведение

- Сохранить исходный запрос. Нормализация регистра/ё/пробелов и дополнительные
  варианты не считаются доказанным исправлением пользовательского ввода.
- Приоритет: priced exact → priced expanded → unpriced exact → unpriced expanded.
  Следующий шаг выполняется только при пустом предыдущем. Ошибка сервиса не означает
  пустую выдачу. available_only остаётся строгим фильтром на всех шагах.
- Expanded использует словарь алиасов/синонимов из tuning, общую транслитерацию
  в обе стороны, гипотезу раскладки и ограниченное fuzzy matching слов. По каждому
  варианту должны совпасть все значимые слова; совпадение одной части не достаточно.
- Цифры, версии и смешанные буквенно-цифровые токены не fuzzy. Однословные
  идентификаторы с цифрами, в том числе 365, не расширяются и не превращаются
  в название бренда. Точный текстовый поиск для них сохраняется.
- Явная десятичная версия после CSP/ЦСП становится строгим Version-фильтром,
  даже если соседний бренд написан с ошибкой; бренд из этого не выводится.
  Алиасы Астра Линукс/КриптоПро учитываются при существующем консервативном разборе.
  Конфликт явного фильтра с запросом или конфликт ролей отклоняется.
- Если десятичный токен не разобран как строгая версия, расширение отключается:
  нельзя исправить название продукта ценой подмены неизвестной версии.
- Не удалять произвольные слова задачи/количества/сроки ради получения выдачи.
  Ограничения, ещё не поддержанные разбором, не объявлять проверенными.

## Лимиты и наблюдаемость

До 5 уникальных вариантов, до 16 значимых токенов в варианте. Для более длинного
запроса расширение отключается целиком, исходный точный запрос не обрезается.
Fuzzy применяется только к буквенным словам длиной от 4: расстояние 1 для 4–5,
2 для 6+ символов, prefix_length=1, max_expansions=3, transpositions=true.
Поля: ProductName/Name/FamilyName; артикулы и описания не исправляются fuzzy.
Запрос передаётся JSON DSL как текст, query_string и пользовательские операторы не исполняются.

CLI показывает версию query policy, варианты-гипотезы, фактически выполненные
шаги и режим найденной выдачи. Это отладочный контракт, публичный OpenAPI не меняется.
Число шагов ≤ 4; каждый использует прежние timeout/проверки partial response,
filters-before-collapse и повторную application-проверку конкретных SKU.
Все шаги вместе с метаданными ограничены общим context timeout 15 секунд;
тайм-аут не выдаётся за отсутствие товаров. Это лимит, не обещание p95.

## Проверка

До реализации: domain-тесты алиасов/раскладки/сохранения чисел/лимитов и конфликта
версии; красный прогон подтверждён отсутствующим QueryPlan. Далее реальные
Elasticsearch-тесты на новых опечатках, транслитерации, неизменности артикула/версии
и fallback. Качество измеряется только на tuning/reference, не на holdout.
Статус независимой разметки не изменяется этим шагом.

Диагностика после сборки CLI:

```powershell
go build -o bin/search.exe ./cmd/search
python scripts/evaluate-tuning.py --output artifacts/tuning-diagnostics.json
python scripts/evaluate-reference.py --output artifacts/reference-diagnostics.json
```

Первый скрипт допускает только development_tuning, не читает holdout и не
передаёт скрытые gold-фильтры вместо пользовательского запроса. Group target,
brand scope и отрицательные примеры считаются отдельно. Условия лицензии
записываются в ungraded_constraints, а не объявляются проверенными.

Реальные ES-тесты также проверяют восстановление потерянного подтверждения
создания: если первый PUT создал индекс, а повтор получил ошибку, Prepare
принимает только полностью совпавший Spec со state staging/ready. Другие
метаданные не принимаются; counts и активация по-прежнему проверяются отдельно.

## Прогон 2026-11-27

На том же активном индексе lexical-v2/families-v2 сравнивались прежняя CLI
legacy_exact и query-v1. Набор из 60 tuning-запросов не менялся между прогонами.

| Диагностика | До | После |
| --- | ---: | ---: |
| Целевая исходная группа в top-4, узкие запросы | 25/52 | 42/52 |
| Брендовый scope в top-4 | 5/6 | 6/6 |
| Пустой ответ на отрицательные примеры | 2/2 | 2/2 |
| Ошибки выполнения tuning | 0 | 0 |

Reference smoke остался 9/10 целей (7/8 семейных и 2/2 vendor/category),
FourFamiliesConfirmed=false на всех исходных 10 примерах. Прогоны сохранены
локально в artifacts/tuning-query-v0.json, tuning-query-v1.json и reference-query-v1.json.
Для узких запросов здесь проверен group_id, а не независимая релевантность
семейства или пригодность лицензии. Данные синтетические, разметка draft;
holdout не запускался. Сложные задачи, редакции/сроки/ёмкости и часть сленга
по-прежнему требуют дальнейшего разбора/семантического поиска.

Семантика fuzzy и лимитов проверена по официальным
[match](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query),
[multi-match](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-multi-match-query)
и [fuzzy](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-fuzzy-query).
