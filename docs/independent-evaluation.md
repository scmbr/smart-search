# Независимое сравнение поиска

Конфигурация `search-freeze-v1` закрепляет исходный commit, SHA backend-файлов,
принятого holdout и локального векторного корпуса, снимок каталога и индекс.
Манифест: [search-freeze-v1.json](../testdata/evaluation/search-freeze-v1.json).
`index_name` в этой версии манифеста — fingerprint из поля результата IndexVersion,
без физического префикса `smart-search-`.

Проверяемый движок: query-v8, lexical-v7, families-v5, hybrid-v2, cosine >= 0.45.
Baseline — текущий лексический поиск с теми же фильтрами и группировкой, а не
реконструкция исторического поиска сайта. Гибрид использует полный корпус,
только кэш эмбеддингов и replay интерпретаций; платные вызовы выключены.

## Процедура

```powershell
go build -o bin/search.exe ./cmd/search
python scripts/evaluate-frozen.py --output artifacts/holdout-cache-only-v1.json
```

Перед первым поиском проверяются SHA всех закреплённых файлов и корпуса.
Один binary используется для обоих режимов; его SHA сохраняется в отчёте.
CLI получает только исходные запросы, без целевых групп, family IDs или меток.
Сначала baseline, затем cache-only hybrid, top-4, priced_first. Порядок запросов
одинаковый; метки используются только после получения выдачи.

Число ответов, каталог, индекс и query policy проверяются для каждого режима.
Unsupported с `not_searched` допустим и учитывается как отсутствие попадания.
Ошибка не превращается в нулевое качество: прогон завершается неуспешно,
частичный артефакт сохраняется. Перезапись существующего отчёта запрещена.
После просмотра нельзя менять правила по промахам этого holdout и объявлять
повторный результат независимым. Для следующего цикла нужен новый набор.

## Метрики и границы

- Отдельно считать group target hit@4 для семейных целей и brand scope hit@4
  для широких запросов. Попадание группы не доказывает пригодность выбранного SKU.
- Сохранять все четыре позиции, исходные ограничения и trace; ограничения
  пока не оцениваются этим runner. Нет оснований заявлять Precision@4/nDCG.
- Отдельно показывать VectorStatus. Промах кэша означает fallback: такой
  прогон измеряет доступный локальный режим, а не качество полного live hybrid.
- Время batch включает загрузку корпуса/CLI и не является p50/p95 запроса.
- Четыре подтверждённых релевантных семейства и verifier остаются отдельными
  критериями; отсутствие рекомендаций не исправляется случайным дополнением.

Офлайн-тесты runner проверяют изменение замороженного источника, смену снимка,
неполный batch и границы brand/top-4. Статус этапа 3 обновляется только по факту
полученного отчёта с явно указанным покрытием векторного кэша.

## Первый результат, 2026-11-28

[Сводка](../testdata/evaluation/holdout-cache-only-v1-summary.json): оба режима
дали 19/34 попаданий целевой группы и 3/6 попаданий brand scope. Hybrid:
39 fallback, один skipped_exact; векторы не участвовали в ранжировании.
Baseline batch 2 977 мс, hybrid 10 102 мс; это не latency SLO.
Полный отчёт локально: artifacts/holdout-cache-only-v1.json, SHA в сводке.
Платных API-вызовов runner не делает. Этап 3 остаётся открытым до полного
гибридного сравнения при той же конфигурации и без настройки по промахам.
Статус not_run внутри исходного замороженного JSON — исторический на момент
заморозки; актуальный факт выполнения фиксируется здесь, без изменения меток.
