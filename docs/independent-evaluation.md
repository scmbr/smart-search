# Независимое сравнение поиска

Конфигурация `search-freeze-v1` закрепляет исходный commit, SHA backend-файлов,
принятого holdout и локального векторного корпуса, снимок каталога и индекс.
Манифест: [search-freeze-v1.json](../testdata/evaluation/search-freeze-v1.json).
`index_name` в этой версии манифеста — fingerprint из поля результата IndexVersion,
без физического префикса `smart-search-`.

Проверяемый движок: query-v8, lexical-v7, families-v5, hybrid-v2, cosine >= 0.45.
Baseline — текущий лексический поиск с теми же фильтрами и группировкой, а не
реконструкция исторического поиска сайта. Гибрид использует полный корпус,
только кэш эмбеддингов и replay интерпретаций; платные вызовы выключены.

## Процедура

```powershell
go build -o bin/search.exe ./cmd/search
python scripts/evaluate-frozen.py --output artifacts/holdout-cache-only-v1.json
```

Перед первым поиском проверяются SHA всех закреплённых файлов и корпуса.
Один binary используется для обоих режимов; его SHA сохраняется в отчёте.
CLI получает только исходные запросы, без целевых групп, family IDs или меток.
Сначала baseline, затем cache-only hybrid, top-4, priced_first. Порядок запросов
одинаковый; метки используются только после получения выдачи.

Число ответов, каталог, индекс и query policy проверяются для каждого режима.
Unsupported с `not_searched` допустим и учитывается как отсутствие попадания.
Ошибка не превращается в нулевое качество: прогон завершается неуспешно,
частичный артефакт сохраняется. Перезапись существующего отчёта запрещена.
После просмотра нельзя менять правила по промахам этого holdout и объявлять
повторный результат независимым. Для следующего цикла нужен новый набор.

## Метрики и границы

- Отдельно считать group target hit@4 для семейных целей и brand scope hit@4
  для широких запросов. Попадание группы не доказывает пригодность выбранного SKU.
- Сохранять все четыре позиции, исходные ограничения и trace; ограничения
  пока не оцениваются этим runner. Нет оснований заявлять Precision@4/nDCG.
- Отдельно показывать VectorStatus. Промах кэша означает fallback: такой
  прогон измеряет доступный локальный режим, а не качество полного live hybrid.
- Время batch включает загрузку корпуса/CLI и не является p50/p95 запроса.
- Четыре подтверждённых релевантных семейства и verifier остаются отдельными
  критериями; отсутствие рекомендаций не исправляется случайным дополнением.

Офлайн-тесты runner проверяют изменение замороженного источника, смену снимка,
неполный batch и границы brand/top-4. Статус этапа 3 обновляется только по факту
полученного отчёта с явно указанным покрытием векторного кэша.

## Первый результат, 2026-11-28

[Сводка](../testdata/evaluation/holdout-cache-only-v1-summary.json): оба режима
дали 19/34 попаданий целевой группы и 3/6 попаданий brand scope. Hybrid:
39 fallback, один skipped_exact; векторы не участвовали в ранжировании.
Baseline batch 2 977 мс, hybrid 10 102 мс; это не latency SLO.
Полный отчёт локально: artifacts/holdout-cache-only-v1.json, SHA в сводке.
Платных API-вызовов runner не делает. Этап 3 остаётся открытым до полного
гибридного сравнения при той же конфигурации и без настройки по промахам.
Статус not_run внутри исходного замороженного JSON — исторический на момент
заморозки; актуальный факт выполнения фиксируется здесь, без изменения меток.

## Полный кэш при неизменном движке

Подготовка выполняется существующим CLI последовательно, по одному запросу:
`bin/search.exe -query <raw-query> -vector-corpus artifacts/vector-corpus.json -live-query -parser-mode live`.
Только для дочернего процесса явно задаётся `OPENAI_LIVE_ENABLED=true`; `.env`
не меняется. Перед подготовкой сверяются frozen SHA и SHA binary первого прогона.
Разрешения D-034/D-037 покрывают новые запросы; общий ledger сохраняется.
Верхний лимит 40 × ($0.001 embeddings + $0.001 parser) = $0.08, включая
резервы внутри каждого Runtime; исходные тексты дают embedding bound $0.00005238.
Parser выбирается существующей политикой, а не ожидаемыми ответами.
При ошибке подготовка останавливается, неопределённые резервы не очищаются.

После подготовки измерение снова выполняется без сети OpenAI:

```powershell
python scripts/evaluate-frozen.py --require-complete --output artifacts/holdout-full-cache-v1.json
```

`--require-complete` запрещает считать прогон завершённым при vector fallback,
catalog mismatch, parser fallback/invalid. `no_candidates` означает выполненный
поиск без соседей выше порога и остаётся допустимым; exact/clarify/unsupported
сохраняют предусмотренные пропуски. Partial/error отчёт сохраняется.
Этот этап завершает ранее закреплённый эксперимент: ни backend, ни порог,
ни маппинг, ни запросы/цели не меняются после первого просмотра результатов.

### Целостность текста и неуспешная подготовка

Все файлы запросов читать с явным `encoding="utf-8"`; системная кодировка
Windows для UTF-8 JSON недопустима. Runner передаёт JSON с ASCII escapes
и проверяет точное равенство возвращённого Query исходному тексту.

Первая подготовка прочитала файл через системную кодировку: 25 запросов
с кириллицей превратились в mojibake. 44 новых вызова стоили $0.00038199;
все резервы закрыты. Эти записи кэша не подменяют правильные ключи и не
используются как доказательство покрытия. Ошибочная попытка сохранена локально
в artifacts/holdout-warmup-live-v1.json. Два последующих replay-прогона
holdout-full-cache-v1/v2 завершились ошибкой полноты и не приняты.
Исходные запросы baseline/cache-only-v1 проверены: все 40 совпадают с метками,
поэтому его исторический результат остаётся действительным.

## Итог полного сравнения, 2026-11-28

[Зафиксированная сводка](../testdata/evaluation/holdout-full-cache-v1-summary.json):

| Режим | Целевая группа hit@4 | Brand scope hit@4 |
| --- | ---: | ---: |
| Baseline | 19/34 | 3/6 |
| Полный hybrid-v2 + parser replay | 18/34 | 3/6 |

Оба нашли цель в 17 случаях; только baseline — в пяти, только hybrid — в четырёх,
оба промахнулись в 14. Превосходство гибрида не подтверждено. На этой небольшой
синтетической выборке нельзя делать вывод о росте конверсии или статистически
доказанной разнице. Baseline остаётся стандартным CLI-режимом, hybrid — явным
экспериментальным. Порог, веса, фильтры и маппинг по этим промахам не меняются.

Векторы: used 35, no_candidates 4, skipped_exact 1; fallback 0. Parser: used 4,
not_selected 36. Все 40 текстов совпадают с исходными. Hits live-подготовки и
replay идентичны; порядок SKU baseline совпал с первым независимым прогоном.
Backend SHA, frozen manifest, корпус, каталог и индекс прежние.

Локальные артефакты: holdout-warmup-live-v2.json и holdout-full-cache-v3.json;
их SHA сохранены в сводке. Batch baseline 2 692 мс, hybrid 11 696 мс — время
с загрузкой процесса/корпуса, не latency SLO и не сопоставление отдельных запросов.

Ledger до задачи: $0.024812375, после: $0.025425085; прирост $0.00061271,
включая неуспешную подготовку $0.00038199 и корректную $0.00023072.
Всего 71 новый вызов. До/после итогового replay одинаково: 478 записей,
25 425 085 nanodollars, незавершённых резервов 0. Повтор не оплачивался.

Независимый эксперимент этапа 3 завершён с отрицательным результатом для
гипотезы общего улучшения. Это не прохождение требований всех четырёх товаров:
назначение/базовые права/совместимость SKU и подтверждённые допродажи остаются
в verifier этапа 4. Следующие изменения качества проверять на development;
этот holdout повторно не объявлять новым независимым набором после настройки.
