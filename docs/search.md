# Поиск и рекомендации

Связанные требования: R-01–R-08, R-11–R-12, N-03–N-06.

## Вход и контекст

Исходный запрос сохраняется неизменным. Контекст включает выбранную категорию,
явный демонстрационный сегмент и историю текущей сессии. По умолчанию профиль
не задан. История — сигнал, а не основание нарушать явно указанные ограничения.
Для демо разрешены синтетические B2B-профили. context.origin=synthetic и profile_id
явно обозначают их; синтетический профиль не выдаётся за историю реального клиента.

Нормализация строит дополнительные варианты, не уничтожая исходный запрос.
Артикулы, номера версий, количество пользователей и сроки сохраняются.
Аббревиатура «мтс» неоднозначна: цель из контрольного набора не становится
универсальной заменой без контекста. Исправления отражаются в ответе.

## Поисковый конвейер

1. Выделить точные идентификаторы и обязательные ограничения.
2. Добавить проверенные синонимы, варианты написания и допустимые исправления.
3. Для сложной формулировки при необходимости запросить структурированную
   интерпретацию модели; не принимать её предположения за явные фильтры пользователя.
4. Получить BM25-кандидатов с приоритетом названия/артикула/категории над описанием.
5. Для смыслового запроса получить вектор и векторных кандидатов.
6. Объединить списки RRF по стабильным идентификаторам и проверить ограничения.
7. Сгруппировать предложения и выбрать подходящий вариант каждой карточки.
8. Применить доступность и подтверждённые бизнес-сигналы среди релевантных вариантов.
9. Добавить рекомендации и объяснения на основании фактических сигналов.

Лимиты кандидатов, параметры RRF, пороги релевантности и необходимость дополнительного
reranker определяются на наборе настройки. Независимый набор оценки не используется
для подбора этих параметров. Бизнес-буст не перекрывает несовместимость лицензии.
По умолчанию availability_policy=priced_first: после проверки релевантности
выбираем предложения с положительной ценой; если таких нет, допускаем варианты
без цены как второй приоритет и ставим unpriced_fallback_used=true.
Среди сопоставимых предложений с ценой available=true имеет преимущество,
но available=false никогда не превращается в доступность под заказ.
Явный available_only отключает запасной режим недоступных предложений.
Для общего запроса о продукте поддержка,
продление и обновление не подменяют новую лицензию: условия права использования
учитываются отдельно. Если роль неизвестна, не обещаем, что это новая лицензия.
Фильтры применяются к предложениям, а не к объединённой смеси параметров группы.
Подготовка признаков реализована политикой [characteristics-v2](normalization.md).
Status=unknown/conflict не удовлетворяет строгому фильтру; evidence=title — извлечение
из названия, а не подтверждение совместимости. Лексический поиск/фильтры реализованы;
правила опечаток и дополнительных вариантов — [query-v1](query-normalization.md).
Векторы/RRF работают с [полным корпусом](vector-corpus.md) и отдельным флагом
live-поиска новых текстов через общий бюджет. Слабые соседи отсекаются hybrid-v2/.45;
при ошибке/промахе кэша действует BM25 fallback. Исторический пилот 512 групп —
[hybrid-v1](hybrid-search.md). [Контракт интерпретации](query-interpretation.md) и
выборочный порт реализованы; [бюджетируемый parser](query-parser-runtime.md)
подключается в CLI явным флагом. Полноценный разбор свободных условий лицензии
и проверка релевантности каждого результата ещё не завершены.

## Выдача

Результаты разделены на основные совпадения, альтернативы и сопутствующие решения.
Для карточки доступны family ID, product ID, выбранный offer ID, название, категория, ссылка,
изображение, известная цена, флаг доступности снимка, условия лицензии и причины выбора.
Неизвестные условия обозначаются неизвестными; цена 0 не показывается как «бесплатно».

По D-018 формируем явный упорядоченный top4 из четырёх разных family_id.
Несколько SKU, версий, редакций или групп одного семейства считаются одним семейством.
Сначала идут точные подходящие семейства; если их два, оставшиеся места заполняются
двумя программно проверенными допродажами других семейств. Альтернативы имеют
отдельную метку и должны удовлетворять заявленным ограничениям/объяснять различия.
top4 содержит ссылки на карточки соответствующих секций, а не отдельные копии.
Если после проверок четырёх семейств нет, возвращаем shortfall_reason и объяснение:
требование количества не выполнено, случайных товаров не добавляем.

Оценка — по первой четвёрке и совпадению семейств, не по точному SKU. Hit@4,
разнообразие family_id, соответствие допродаж и корректность выбранных лицензий
важнее отдельного Hit@1; последний остаётся диагностической метрикой.

Пустой ответ означает отсутствие достаточных совпадений, а не доказанное отсутствие
товара в магазине. Отличаем отсутствующий продукт от отсутствия подходящей лицензии
и временной ошибки сервиса. При неоднозначности предлагаем варианты уточнения.

## Подсказки

Локальный поиск по словарю названий, категориям и синонимам. Генеративная модель
не вызывается на каждую букву. На frontend — debounce, отмена/игнорирование
устаревших запросов и управление клавиатурой. Значение задержки измеряется позже.
Запрос подсказки не считается отправленным поиском.

## Доказательства рекомендаций

Смысловая близость не является подтверждением совместимости. Рекомендация имеет
тип связи, объяснение, источник, дату проверки и ограничения версий/платформ.
Проверенные источники готовятся заранее; контент не исполняется как инструкции.
LLM не может вводить неизвестные товарные ID, изменять цены или обещать поддержку.
Если источник недоступен/не подходит к версии, утверждение совместимости не показывается.
Сравнение цен конкурентов и «часто покупают вместе» не заявляются без соответствующих данных.

Для каждой допродажи backend выполняет детерминированные правила на нормализованных
характеристиках выбранной пары SKU: платформа, версия, архитектура, количество
пользователей/узлов, тип лицензии и допустимость её покупки в данном контексте.
Набор обязательных правил зависит от связи; проверка только наличия URL не достаточна.
Выходы проверки: passed/failed/unknown. В recommendations допускается только passed
по всем обязательным правилам; неизвестное поле не считается совпадением. В trace
можно показать причины отклонения без утверждения совместимости.
Отчёт verification содержит anchor_offer_id, recommended_offer_id, время проверки,
rule_id, поле, оператор, ожидаемое/фактическое значение и источник каждого правила.
Смена версии/выбранного SKU требует новой проверки, старый отчёт не переносится.
LLM может извлекать кандидатов, но не исполняет код правил и не устанавливает passed.
Данные из feed и проверенных источников могут быть подготовлены заранее; онлайн-сбор
на каждом запросе не требуется. Цены и акции относятся к дате снимка.

Примеры источников для последующей проверки конкретных версий:
- [Кибер Бэкап и Astra Linux](https://cyberprotect.ru/podderzhivaemyie-texnologii/cyber-backup-astra-linux-specialedition/)
- [Совместимое ПО Astra](https://astra.ru/ready-for-astra/compatible-software/)

## Разбор запроса

Отдельное представление показывает исходный/нормализованный запрос, применённый
контекст, кандидатов каждого способа, фактические причины выбора, длительности
и ограниченный режим. Не раскрывает секреты и внутренние рассуждения модели;
объяснения описывают наблюдаемые этапы и проверенные основания.
