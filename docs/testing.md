# План тестирования и оценки

Матрица ниже описывает поведенческие тесты приложения, часть ещё предстоит реализовать.
В internal/catalog уже есть тесты XML/gzip, точных цен, диагностики, лимитов,
отмены, ошибок sink и передачи предложений до конца входа. CLI проверяет коды
выхода и JSON для валидного/невалидного каталога и неполного stdin. Эти тесты
написаны до реализации; начальные прогоны упали на отсутствующих символах,
после реализации прошли. Сохранение снимка в БД пока не тестируется и не реализовано.

Также добавлены
исполняемые проверки контракта и тестовых данных в [contracts](../contracts/):
валидация OpenAPI и положительных/отрицательных примеров, HTTP-запросов по схеме,
инварианты примеров выдачи, происхождение исходных целей и разделение семейств
между tuning/holdout. Они не подтверждают работу ещё не созданного сервера/импортёра.

Запуск: `go test ./...`, статическая проверка: `go vet ./...`. Используется
kin-openapi v0.151.0; тестам не нужны Docker, исходные вложения и OpenAI API.
Синтетические fixtures описаны в [testdata/README.md](../testdata/README.md).
Проверка контракта не заменяет поведенческие тесты. Часть T-01/T-03 реализована
reader-тестами, T-02 (повторный импорт/снимки) и поисковые сценарии остаются будущими.

Проверено 2026-11-26 на Windows, Go 1.27.3: `go test -count=1 ./...`, `go vet ./...`,
`go mod verify` прошли; `gofmt -l contracts` не вывел файлов. Дополнительно проверены
Markdown-ссылки, JSON fixtures и точное совпадение всех 10 исходных пар запрос/URL
с XLSX. Платные API и Docker не использовались. Результат относится к контракту
и данным, не к качеству ещё не реализованного поискового движка.

После добавления reader/CLI также прошли `go test -count=1 -cover ./...` и `go vet ./...`.
Покрытие reader/валидатора — 89,6%, CLI — 73,2%. На полном feed проверены
136 040 предложений и 9 311 категорий без отклонений и диагностик. Это не тест
транзакций БД, индексации, рекомендаций или семантической релевантности.

## Уровни

- Go testing: нормализация, ограничения, RRF, группировка, события и валидация.
- Go httptest: контракт HTTP и ошибки с подменой внешних клиентов.
- Интеграционные: реальные PostgreSQL/Elasticsearch с малыми fixtures, без OpenAI.
- Vitest: логика UI и защита от устаревших ответов.
- Playwright: поиск, карточки, подсказки, аналитика и режим разбора.
- Отдельный live/evaluation набор: OpenAI только при явном запуске и лимите расходов.

## Данные оценки

Начальный набор — 10 строк из предоставленной таблицы. Цели содержат страницы
продуктов и категории, поэтому сравнение по одному URL предложения недостаточно.
До оценки сопоставить цели с группами/категориями feed и проверить их доступность.
Начальное сопоставление 10 целей с группами, vendor/category и примерами SKU
сохранено в source-queries.json. Оно не доказывает пригодность любого SKU группы:
сохраняются ограничения платформы, версии и роли предложения.

Добавить опечатки, сленг, смешанные языки, запросы по задаче, ограничения лицензий,
неоднозначные и неизвестные запросы. Отделить набор настройки от независимой
оценки; варианты одной исходной формулировки не распределять случайно между ними.
Ожидаемые цели фиксировать до просмотра результатов на независимом наборе.

Baseline — заранее описанный простой лексический поиск. Это наша воспроизводимая
точка сравнения, а не измерение действующего поиска Softline.
Дополнительно сравнить BM25 без векторов, векторы и гибридный вариант на одном наборе.

Основные метрики по D-018: Family Hit@4, Precision@4 и nDCG@4 при наличии разметки,
число разных семейств в top4 и доля программно проверенных допродаж. Hit@1/MRR
остаются диагностическими. Для категории/vendor-page в исходном Excel перед оценкой
размечаем допустимые семейства; попадание в произвольную широкую категорию недостаточно.
Также измеряем долю без релевантных совпадений, нарушения ограничений,
покрытие обязательных характеристик, p50/p95 и стоимость. Всегда указывать число
примеров; по десяти запросам не делать вывод о качестве всего каталога.

## Производительность и готовность

Фиксировать характеристики компьютера, версии, размер индекса, concurrency,
холодный/прогретый кэш, доступность API и отдельно подсказки/поиск/индексацию.
Численные пороги утверждаются после пилота и до финальной приёмки.
На текущем этапе gofmt/go test/go vet применяются к пакету контрактных тестов;
frontend-проверки появятся вместе с интерфейсом.
