## D-014. Лимит расходов OpenAI API

- Дата: 2026-11-26.
- Статус: **принято**, пользователь установил лимит 5 USD.
- Контекст: нужен предел расходов на разработку, а не баланс аккаунта.
- Решение: суммарные расходы проекта на первоначальную индексацию, эксперименты
  и живые проверки API ограничены 5 USD. До массовой индексации оцениваем расход
  на выборке; последующие вызовы учитывают уже потраченное и резерв на запросы в работе.
- Последствия: тесты по умолчанию не используют платные API; возможность обработать
  полный каталог в пределах лимита подтверждается расчётом, а не предполагается.
- Альтернатива: неограниченные расходы отклонены. Изменение лимита требует решения
  пользователя. Генеративная модель пока не выбрана.

## D-015. Доступность и нулевые цены в MVP

- Дата: 2026-11-26.
- Статус: **заменено D-018** в части строгого исключения недоступных предложений;
  историческое решение сохраняется ниже. Уточнение семантики нуля
  не является блокером текущего этапа.
- Решение: по умолчанию поиск выбирает available=true. В исследованном снимке все
  такие предложения имеют положительную цену. Недоступные записи сохраняются
  для анализа и альтернатив, а нулевая цена отображается как неизвестная.
- Последствия: нули не участвуют в сравнении выгодности; не делаем вывод, что
  любое unavailable предложение имеет нулевую цену. Внешняя семантика поля может
  быть уточнена позднее, если появится сценарий заказа недоступных товаров.
- Альтернатива: удалить unavailable записи полностью — отклонена, так как теряются
  данные для объяснения отсутствия и анализа спроса.

## D-016. Переход к контрактам с явными допущениями

- Дата: 2026-11-26.
- Статус: **принято** для этапа спецификаций и тестовых данных.
- Контекст: пользователь разрешил продолжать после обсуждения ограничений.
- Решение: D-004–D-013 используются как рабочая архитектура; отсутствие логов,
  ответа о четырёх товарах и готового Docker не блокирует офлайн-проверки контракта.
  Эти проверки не запускают модели и не требуют бизнес-метрик.
- Последствия: Docker проверяется до интеграционных тестов этапа 2, а не объявляется
  готовым заранее. Ответ о четырёх товарах ожидается; до него действует правило R-05.
  Точные версии сервисов и выбор генеративной модели не считаются согласованными.
- Альтернатива: ждать всех внешних ответов до контрактов — отклонена как ненужная задержка.

## D-017. Проверяемый контракт и подготовка тестов

- Дата: 2026-11-26.
- Статус: **базовый вариант**.
- Решение: OpenAPI 3.0.3 в docs/openapi.yaml; Go не ниже 1.25; тестовый валидатор
  kin-openapi v0.151.0. HTTP API и импортёр на этом этапе не реализуются.
- Последствия: схема и примеры проверяются автоматически без Docker/OpenAI.
  Область проверки fixtures явно отделена от поведенческих тестов приложения.
  API использует цены в целых копейках и явное неизвестное значение, cursor pagination
  и идемпотентность отправки поиска/событий. Контракт сохраняет роль предложения
  (новая лицензия, продление, обновление, поддержка, неизвестно).
- Альтернатива: только текстовый API без схемы — отклонена из-за риска расхождений.

## D-018. Уточнения экспертов: семейства, запасная выдача и проверка допродаж

- Дата: 2026-11-26.
- Статус: **принято по ответам экспертов**, переданным пользователем.
- Основание: [10 ответов и операционная трактовка](docs/expert-answers.md).
- Решение: целевой ответ — топ-4 разных семейств. При нехватке прямых совпадений
  включаем проверенные допродажи с явной меткой. Эталон сопоставляем на уровне
  семейства/группы, SKU служит выбором подходящей лицензии внутри него.
- Предложения без цены — второй приоритет при отсутствии подходящих предложений
  с ценой; отсутствие наличия не превращаем в обещание заказа. Вводим явную
  политику priced_first (по умолчанию) или available_only (по выбору пользователя).
- Для допродаж обязательна программная проверка характеристик и условий конкретных
  предложений. Ссылка сама по себе недостаточна; неизвестные обязательные данные
  не считаются подтверждением. Цены и акции берём из снимка, онлайн-сбор не нужен.
- Синтетические B2B-профили разрешены и явно обозначаются. Агентный цикл необязателен.
- Отдельный интерфейс аналитики — бонус. Сохраняем его как выбранную функцию демо;
  прежнее обоснование обязательности в D-004 уточнено этим решением.
- Последствия: меняются R-04–R-07, R-10, контракт до реализации (версия 0.2.0),
  примеры выдачи, метрики @4 и тесты. family_id не обязан совпадать с group_id.
- Альтернативы: четыре лицензии одной семьи, жёсткое исключение всех available=false,
  оценка только по топ-1 и рекомендации только по ссылке отклонены уточнениями.

## D-019. Потоковый reader до сохранения снимков

- Дата: 2026-11-26.
- Статус: **принято для текущего шага реализации**, пользователь разрешил продолжить.
- Контекст: контракт API и fixtures подготовлены; независимая разметка семейств
  ещё проверяется, Docker не подтверждён. Это не мешает тестировать чтение feed.
- Решение: реализовать пакет internal/catalog и CLI catalog-check на стандартной
  библиотеке Go. Сначала написать поведенческие тесты и подтвердить красный прогон,
  затем reader и команду. Поддержать plain XML/gzip, точные цены, диагностику,
  ограничение ресурсов, отмену и потоковые callbacks без платных API.
- Последствия: Read даёт предварительные записи и отчёт. Sink обязан писать в
  staging; отсутствие ошибок не является активацией снимка. Идемпотентность,
  транзакции, возобновление и PostgreSQL будут отдельным шагом. Роль лицензии,
  версия и family_id не угадываются по source group_id.
- Альтернатива: загружать XML целиком или сразу смешать парсинг с БД/Elasticsearch —
  отклонена для независимой проверки и ограниченной памяти.

## D-020. PostgreSQL staging и возобновление записи

- Дата: 2026-11-26. Статус: **принято для текущего шага**.
- Контекст: reader проверен на полном feed; Docker 29.9.3 и PostgreSQL 17.12
  проверены после восстановления запуска Docker Desktop. Доступно 16 ГБ RAM,
  Docker VM выделено около 8 ГБ.
- Решение: PostgreSQL 17.12-bookworm, pgx v5.11.0; PostgreSQL License и MIT.
  godotenv v1.5.1 (MIT) загружает .env без замены переменных процесса.
  Лимиты контейнера 1 ГБ/2 CPU; Elasticsearch подключается следующим шагом.
- Domain задаёт валидность снимка и repository port; application управляет
  порциями/повторами; инфраструктура адаптирует reader и pgx; cmd собирает зависимости.
- Идентичность — SHA-256 источника и версия нормализации/лимитов. Приватная
  временная копия защищает импорт от изменения оригинала. CopyFrom и checkpoint
  фиксируются одной транзакцией, writer сериализуется advisory lock.
- Возобновление повторно валидирует весь XML/gzip и пропускает сохранённый префикс.
  Финальная транзакция сверяет счётчики и переключает active. Повтор ready — no-op,
  завершённые invalid не активируются. Миграции forward-only с проверкой checksum.
- Альтернативы: одна транзакция на весь feed, запись прямо в active и seek внутрь
  XML/gzip отклонены из-за длительных транзакций и риска неполного каталога.
- Последствия: дополнительный диск размером с источник, повторное чтение при retry;
  старые снимки и остатки временных файлов после аварий пока удаляются вручную.
- Источники версий/лицензий: [PostgreSQL](https://www.postgresql.org/docs/17/release-17-12.html),
  [PostgreSQL License](https://www.postgresql.org/about/licence/),
  [pgx](https://github.com/jackc/pgx/releases/tag/v5.11.0),
  [pgx MIT](https://github.com/jackc/pgx/blob/v5.11.0/LICENSE),
  [godotenv MIT](https://github.com/joho/godotenv/blob/v1.5.1/LICENCE).

## D-021. Детерминированные характеристики перед поисковым индексом

- Дата: 2026-11-26. Статус: **принято для текущего шага**.
- Контекст: в 125 699 из 127 828 параметров «Версия» указано неизвестное значение;
  остальные часто содержат редакцию. Поле архитектуры/платформы содержит x86-64,
  Эльбрус и ARMv8, а не подтверждённые ОС. Лицензии внутри группы различаются.
- Решение: characteristics-v2 в domain, вызов из application импорта до staging.
  Сохранять тип продукта, роль, тип лицензии, версию/редакцию, архитектуру/платформы,
  пользователей/узлы с known/unknown/conflict, rule ID и исходным evidence.
- Строгие словари/единицы и узкие правила названий КриптоПро CSP/Astra Linux;
  не извлекать произвольные числа и не наследовать свойства между SKU.
  Подписка/add-on не означают новую лицензию. Версия из названия не доказывает
  совместимость; отсутствие данных не заполняется моделью или description.
- Версия политики входит в identity снимка: повторная загрузка создаёт новый
  проверяемый снимок, старый сохраняется до атомарной активации нового.
  SQL-структура неизменна, JSONB расширяется аддитивно.
- Альтернативы: классификация LLM всех 136 тысяч SKU, угадывание по цене/group_id
  и массовая перезапись active отклонены из-за бюджета, неоднозначности и риска потери данных.
- Последствия: покрытие числовых версий/ОС консервативно и измеряется отдельно;
  конфликты признаков не являются XML-ошибками и не делают сырые записи invalid.
  Семейства, фильтрация поиска и verifier — отдельные следующие задачи.

## D-022. Первый лексический индекс и CLI

- Дата: 2026-11-27. Статус: **принято для текущей реализации**, результаты прогонов
  фиксируются отдельно в docs/lexical-baseline.md.
- Решение: Elasticsearch 9.5.7, официальный низкоуровневый elastic-transport-go
  v8.11.0; JSON DSL формируется адаптером и проверяется HTTP/integration-тестами.
  Типизированный генератор полного Elasticsearch API пока не подключается.
- Дистрибутив Docker поставляется по ELv2, локальный узел использует basic;
  транспорт — Apache-2.0. Платные функции/ML не используются. Single-node,
  1 shard/0 replicas, 2 ГБ RAM/2 CPU, JVM heap 512 МБ, mmap отключён без изменения WSL.
  Порт 9200 доступен только на 127.0.0.1, сервис включается Compose-профилем search.
- PostgreSQL-снимок фиксируется на время чтения; индекс идентифицируется снимком,
  нормализацией, lexical-v2 и каноническим JSON маппинга семейств. Порции, проверка
  count, write block и атомарная замена alias сохраняют прежнюю рабочую выдачу при сбое.
- Начальные правила семейств имеют явные group IDs/vendor scope/источник. Остальные
  группы остаются provisional и не доказывают выполнение четырёх семейств.
- Baseline — BM25, CamelCase, русский stemming/stop words, фильтры конкретного SKU
  до collapse и повторная проверка результата в application. Без query_string/LLM.
  ES hit count не считается числом семейств. Исходные 10 примеров — reference smoke.
- Альтернативы: публиковать недостроенный индекс, считать каждый SKU семейством,
  использовать цену поддержки как базовую лицензию и подмешивать случайные товары
  отклонены требованиями данных/топ-4. Рекомендации/verifier и публичный HTTP API — далее.
- Источники: [версия сервера](https://www.elastic.co/docs/deploy-manage/upgrade/deployment-or-cluster/upgrade-elasticsearch-docker),
  [лицензирование](https://www.elastic.co/pricing/faq/licensing),
  [транспорт](https://github.com/elastic/elastic-transport-go/tree/v8.11.0),
  [collapse и ограничения счётчиков](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/collapse-search-results).

## D-023. Этап 1: evidence семейств и раскрытый holdout

- Дата: 2026-11-27. Статус: принято для baseline; независимая разметка pending.
- Контекст: семейства бывшего holdout использованы при настройке lexical-v2;
  исходный набор больше не может подтверждать независимое качество.
- Решение: сохранить сценарии и original_split, перевести бывший holdout в regression,
  явно отметить отсутствие проверенного независимого набора. Новый draft holdout-v2
  (8 запросов/4 других семейства) заморожен до просмотра выдачи; проверка разметки
  остаётся открытой, без автоматического объявления успешной оценки по CI.
- Маппинг families-v2 объединяет стандартную/расширенную редакции Кибер Бэкап:
  группы 173614 и 173615. Сведения о 10 семействах/11 группах/1 866 предложениях
  извлекаются из feed отдельно от поиска и фиксируются малым evidence JSON с SHA.
  Неизвестные группы остаются provisional; полный каталог не объявляется размеченным.
- Один family_id не может иметь противоречащие имя/vendor scope/источник: такая
  конфигурация отклоняется. Ошибка воспроизведена тестом до исправления.
- Последствия: маппинг меняет fingerprint физического индекса; старый индекс не
  перезаписывается. Карточки разных редакций одного семейства не заполняют топ-4.
  Принадлежность к семейству не доказывает права на лицензию/версию или совместимость.
- Порядок независимой проверки и команды: [evaluation-review.md](docs/evaluation-review.md).

Для каждого нового решения добавлять ID, дату, статус, контекст, выбранный вариант,
отклонённые альтернативы и последствия. Изменённое решение не удалять: отмечать
его как заменённое и ссылаться на новый ID. Не считать гипотезу измеренным фактом.
